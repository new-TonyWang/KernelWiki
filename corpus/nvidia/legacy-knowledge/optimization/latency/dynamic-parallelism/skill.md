## S1: Use CDP2 for Recursive or Irregular Workloads

**When to Use:** When the amount of parallel work is data-dependent and cannot be determined before kernel launch (e.g., adaptive mesh refinement, tree traversal, sparse graph algorithms).

**How to Apply:**
1. The parent kernel evaluates the workload and launches child grids where needed.
2. Child grids inherit global memory pointers from the parent.
3. Use `cudaStreamTailLaunch` to access child grid results (CDP2 semantics).

**Code Template:**
```cpp
__global__ void adaptiveRefine(float* data, int level, int maxLevel) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;

    float error = computeError(data, tid);

    if (error > threshold && level < maxLevel) {
        // Launch child grid to refine this region
        int childN = getChildWorkSize(tid);
        if (threadIdx.x == 0) {
            adaptiveRefine<<<(childN+255)/256, 256>>>(
                data + getChildOffset(tid), level + 1, maxLevel);
        }
    }
}
```

> Source: PG 4.18.1 -- "Data-dependent parallel work can be generated by a kernel at run-time."

## S2: Use Tail Launch for Accessing Child Grid Results

**When to Use:** When the parent needs to process results produced by child grids. In CDP2, `cudaDeviceSynchronize()` is removed; tail launch is the mechanism.

**How to Apply:**
1. Launch a "tail" kernel into `cudaStreamTailLaunch` from the parent.
2. The tail kernel runs after all child grids complete.
3. The tail kernel can safely read child grid modifications to global memory.

**Code Template:**
```cpp
__global__ void tailProcess(float* data) {
    // Safe to read data modified by child grids
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    data[tid] = postprocess(data[tid]);
}

__global__ void parentKernel(float* data) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    data[tid] = preprocess(tid);
    __syncthreads();

    if (threadIdx.x == 0) {
        childKernel<<<childGrid, childBlock>>>(data);
        tailProcess<<<tailGrid, tailBlock, 0, cudaStreamTailLaunch>>>(data);
    }
}
```

> Source: PG 4.18.3.1 -- "The only way to access the modifications made by the threads in the child grid before the parent grid exits is via a kernel launched into the cudaStreamTailLaunch stream."

## S3: Minimize Child Grid Launch Overhead

**When to Use:** When CDP launch overhead is a concern relative to child grid work size.

**How to Apply:**
1. Batch work: have one thread per block launch the child grid rather than every thread.
2. Ensure child grids have enough work to amortize the launch cost.
3. Use named streams for concurrency between child grids from different blocks.

**Code Template:**
```cpp
__global__ void parentKernel(float* data, int* workSizes) {
    // Only one thread per block launches children
    if (threadIdx.x == 0) {
        int myWork = workSizes[blockIdx.x];
        if (myWork > MIN_CHILD_WORK) {
            childKernel<<<(myWork+255)/256, 256>>>(
                data + blockIdx.x * stride, myWork);
        }
    }
}
```

> Source: PG 4.18 -- CDP launches incur overhead; batch when possible.

## Cascading Opportunities

- For workloads that can be pre-determined, prefer `cuda-graphs` with device launch over CDP.
- `work-stealing` (Blackwell cluster launch control) provides a more efficient alternative for load balancing.

## Conflicts

- **cuda-graphs:** CUDA Dynamic Parallelism is not permitted within device graph kernel nodes.
- CDP overhead can be significant for small child grids.

## Principles

1. **CDP2 is the default since CUDA 12.0:** CDP1 is deprecated. No `cudaDeviceSynchronize()` from device code in CDP2 (PG 4.18.1.1).
2. **Parent-child memory coherence is one-way at launch:** Child sees parent's memory state at launch time, but parent cannot see child modifications without tail launch (PG 4.18.3.1).
3. **Streams and events are grid-scoped:** Device-side streams created in a grid are only valid within that grid (PG 4.18.2.3).
