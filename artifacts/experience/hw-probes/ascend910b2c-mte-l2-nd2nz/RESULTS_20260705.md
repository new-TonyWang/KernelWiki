# 910B MTE/ND2NZ microbenchmark report

## Method

- Hardware: Ascend 910B2C, device id 3, CANN 9.0.0.
- Launcher: generated ACLNN custom op, timed with `aclrtEventElapsedTime` around repeated kernel launches.
- Tile: fp16 32 KiB per loop (`bytesPerLoop=32768`).
- Large-shape default: 16 MiB input (`nelems=8,388,608 fp16`).
- Main timing below uses `loops=4096`, 5 repeats, after 1 warmup. Logical traffic is counted as requested transfer bytes, not physical cache-line traffic.

## Main results, loops=4096

| mode | path | avg us | logical traffic | logical GB/s |
|---:|---|---:|---:|---:|
| 0 | MTE2 `LoadData` GM/L2 -> L0A | 446.688 | 128 MiB | 300.46 |
| 1 | MTE2 `DataCopy` GM/L2 -> L1 raw | 902.024 | 128 MiB | 148.80 |
| 2 | MTE2 `DataCopy(Nd2NzParams)` GM ND -> L1 NZ | 1161.284 | 128 MiB | 115.57 |
| 3 | same AIC: GM/L2 -> L0A + GM/L2 -> L1 | 1394.984 | 256 MiB | 192.43 |
| 4 | MTE1 `LoadData` L1 -> L0A | 364.852 | 128 MiB | 367.82 |
| 5 | MTE1 `LoadData` L1 -> L0B | 655.820 | 128 MiB | 204.65 |
| 6 | same AIC: L1 -> L0A + L1 -> L0B | 953.852 | 256 MiB | 281.40 |
| 7 | GM/L2 -> L0A with `ifTranspose=true` | 441.676 | 128 MiB | 303.87 |
| 8 | prototype combined transpose: GM ND->L1 NZ then L1->L0A | 1525.692 | 256 MiB | 175.96 |

## Contention observations

- MTE2 GM/L2->L0A and GM/L2->L1 on the same AIC: mode 3 time is 1394.98 us, close to mode0+mode1 = 1348.71 us. This indicates no independent doubling; the two paths mostly serialize/share upstream bandwidth, with ~3.4% extra overhead in this microkernel.
- MTE1 L1->L0A and L1->L0B: mode6 time is 953.85 us vs mode4+mode5 = 1020.67 us. They can overlap modestly; total throughput is lower than L0A alone but not a complete single-pipe serialization.

## L2/cache-hit effects

Two L2 experiments were run.

1. **Hot repeated sweep, fixed logical traffic 128 MiB**: working-set allocation 32 KiB..64 MiB, `loops=4096`. With one warmup, GM/L2->L0A stays about 291–315 GB/s and GM/L2->L1 stays about 138–149 GB/s. This is the cache-hit/streaming steady state.
2. **Cold vs hot on GM/L2->L0A**: without warmup, 128 MiB logical traffic costs ~0.93–1.21 ms for 32 KiB..64 MiB allocation; with warmup it costs ~0.42–0.47 ms. So cache hit roughly gives a 2.2x speedup for this MTE2->L0A path.
3. **Capacity cliff probe with full hot working set** (`loops = working_set / 32 KiB`):

| hot working set | loops | avg us | logical GB/s |
|---:|---:|---:|---:|
| 128 MiB | 4096 | 437.82 | 306.55 |
| 160 MiB | 5120 | 546.80 | 306.82 |
| 192 MiB | 6144 | 866.44 | 232.37 |
| 224 MiB | 7168 | 1486.34 | 157.95 |
| 256 MiB | 8192 | 1927.02 | 139.31 |

The cliff starts between **160 MiB and 192 MiB** for this path/access pattern. I would treat the effective usable L2/SLC capacity seen by this single-core MTE2 stream as roughly **160 MiB**, with a transition region up to ~192 MiB. This is an empirical capacity, not a public spec claim.


## Cross-cube L2/SLC reuse

A follow-up test was added to check whether L2/SLC hot data can be reused across cube cores. Two extra modes were used:

- `mode=20`: `blockDim=2`; two cube cores issue GM/L2 -> L0A `LoadData` from the same addresses.
- `mode=21`: `blockDim=2`; two cube cores issue GM/L2 -> L0A `LoadData` from shifted/disjoint-ish addresses.

Representative results:

| working set | warmup | 1 cube mode0 | 2 cubes same addr mode20 | 2 cubes shifted addr mode21 |
|---:|---:|---:|---:|---:|
| 16 MiB | cold | 636.99 us | 638.81 us | 643.84 us |
| 16 MiB | hot | 443.91 us | 441.35 us | 451.45 us |
| 128 MiB | hot | 453.37 us | 452.41 us | 450.76 us |
| 256 MiB | hot | 442.00 us | 463.01 us | 452.86 us |

Conclusion: **L2/SLC hot data is visible across cube cores**: two cubes reading hot data finish in nearly the same wall time as one cube for the same per-cube loop count, so the cache is not behaving like a strictly private per-cube cache. However, **same-address simultaneous reads did not show a strong additional multicast/reuse advantage** over shifted/disjoint-ish reads; mode20 and mode21 are usually close. Practically, arrange temporal locality so neighboring cubes consume recently loaded tiles, but do not rely on same-line multi-cube reads for a large extra speedup. Keeping the working set under the earlier ~160--192 MiB effective hot-capacity region remains the more important optimization.

Detailed cross-cube evidence is in `host_results/CROSS_CUBE_L2_REPORT.md`; raw data is in `host_results/cross_cube_l2_raw.txt`.

## A transpose conclusion

For the tested large-shape A-transpose-like paths, direct GM/L2 -> L0A `LoadData` with `ifTranspose=true` (mode7) is best for one-use A tiles: 441.68 us, effectively equal/slightly faster than non-transpose mode0. The two-stage path GM ND->L1 NZ + L1->L0A (mode8) is much slower for one use (1525.69 us).

A useful rule from the measured rates:

- direct transpose to L0A: ~303.9 GB/s;
- GM ND->L1 NZ: ~115.6 GB/s;
- L1->L0A: ~367.9 GB/s.

If an A tile is reused `R` times, the amortized two-stage cost per use is approximately `1/115.6/R + 1/367.9` ns/byte, while direct is `1/303.9` ns/byte. The crossover is **R ≈ 16**. Thus:

- **R < ~16**: use direct GM/L2 -> L0A transpose (`LoadData(ifTranspose=true)`) and avoid L1 staging.
- **R >= ~16**: pretransform/cache A as NZ in L1, then feed L0A from L1; pipeline GM->L1 for future tiles with L1->L0A for current tile, because steady-state is bottlenecked by the slower ND2NZ load.
- Splitting a one-use tile across both paths is not beneficial in this measurement; the slower ND2NZ/L1 path drags down total throughput.
